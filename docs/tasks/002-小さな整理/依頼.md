# 002 小さな整理（動作を変えない）

作業ブランチ: refactor/tidy（作成済み。ブランチの切り替え・コミットはしない。Claudeがコミットする）。
前提資料: docs/tasks/001-コード調査/結果.md（あなた＝Solが前回書いた調査）。特に「6．整理案」の案Aと「2．変更時に守る識別子」。

## ねらい

これから機能を足していくための土台。整形・lint を検証コマンドで守らせ、重複と紛らわしい名前を減らし、大きいファイルを読みやすく分ける。
利用者から見た動作は一切変えない。

## やること

1. 検証コマンド
   - Biome 2.6.3 は devDependencies に固定済み（bun.lock あり。新しい依存は足さない。ネットワークは使えない）。
   - biome.json を作る。既定設定を基本に、`noUndeclaredVariables` を有効、`chrome` を拡張側（background・isolated・probe）だけ global にする。MAIN world のファイルでは `chrome` を使っていないことが検査で分かるようにする。
   - 改行: このリポジトリは core.autocrlf=true。`.gitattributes` に `* text=auto` を置き、Biome の `formatter.lineEnding` は `"auto"`。Markdown は Biome の対象から外す（docs/ と README は整形しない）。
   - scripts/ に小さな検査を置く（bun で動く JS）: manifest.json に書かれたファイルがすべて存在すること、src/ の全 JS が構文として正しいこと。エラー文には直し方を書く。
   - package.json の `scripts.check` に `biome check` と上の検査をまとめ、`bun run check` 1つで全部が走るようにする。
2. 整形と lint の違反をなくす
   - 整形は自動でよい。lint の指摘は1件ずつ、動作が変わらない直し方を選ぶ。動作が変わるおそれがあるもの（例: review-ui.js の innerText→textContent、fetch/XHR ラッパーの arguments の扱い）は、直さずに理由を書いて biome-ignore で個別に抑える。
   - probe.js は普通の書き方（1文1行、意味のある変数名）に戻す。
3. 重複をまとめる（同じ world の中だけ）
   - ISOLATED: storage キー、メッセージのマーカー、HOST_ID、ユーザーキーの正規化（canonicalUserKey / canonical）を共有の1ファイルにまとめ、manifest の先頭に足す。共有は window 上の1つの名前空間オブジェクトで、名前は既存の `__xfr...` の型に合わせる。
   - MAIN: `walk` など、まとめても戻り値が変わらないものだけ。違いがあるもの（List 抽出の fallback など）は無理にまとめない。
   - 保存キーの文字列・保存データの形・メッセージの中身は1文字も変えない。
4. 大きいファイルを分ける
   - review-ui.js から CSS 文字列を別ファイルへ（Shadow DOM への挿入方式はそのまま）。
   - graphql-page.js から、レスポンスの解析（User/Tweet/List の正規化、cursor 抽出、再帰探索）を別ファイルへ。
   - fetch/XHR のフックの順番（manifest の MAIN の並び）は変えない。新しいファイルを足すときは、フックを持たないファイルとして置き、既存のフックの相対順を保つ。
5. 紛らわしい内部名を直す（調査結果の 2. の「揃える価値がある箇所」から）
   - 例: themeTimer→layoutTimer、bridge.js→probe-bridge.js、TTL 定数に単位（_MS）、nativeFetch が実際は直前の fetch であることが分かる名前、xfr-bookmarks-placeholder の誤用。
   - 表示テキスト（Review Mode、通常表示、★、リスト など）は他のファイルが判定に使っているので変えない。DOM の id/class を変えるなら参照元をすべて同時に直す。
6. テスト（bun test）
   - 分けた解析の関数に、小さな手書きの fixture でテストを足す（X に通信しない）。content script はモジュールではないので、テストからの読み込み方は既存の形を壊さない方法を選ぶ（例: ファイルを読み込んで評価し、名前空間から取り出す）。
   - `bun run check` にテストも含める。
7. 文書
   - AGENTS.md を新しく作る（50行程度まで）。読む順番（docs/ARCHITECTURE.md、docs/進み具合.md）、検証コマンド、禁止事項（Codex はコミットしない、検証コマンドと scripts/ の検査を勝手に変えない、保存キーと保存形式を移行なしに変えない、認証ヘッダー・Cookie・CSRF を保存・出力しない）、「コードから分からない決まり」（調査結果 7. の箇条書きのうち、コードで確かめられたものだけ。時刻と期間はミリ秒、ユーザー索引は @ 付き小文字、など）。
   - docs/ARCHITECTURE.md のファイル一覧を新しい構成に合わせる。
   - docs/進み具合.md を作る（今の状態、次にやること）。

## 確認方法

- `bun run check` が通ること（出力を結果ファイルに貼る）。
- 変更前後で、manifest の MAIN/ISOLATED それぞれの読み込み順が、既存ファイルの相対順を保っていること（結果ファイルに前後の並びを書く）。
- 保存キー・メッセージのマーカー・action 名を grep して、変更前と同じ集合であること（結果ファイルに書く）。

## やってはいけないこと

- 動作の変更、不具合の修正（調査で見つけた候補の不具合も、今回は触らない。気づいたことは結果に書く）。
- 依存の追加・更新、git のコミット・ブランチ操作・push。
- X への通信、本人のブラウザ・クリップボード・ほかのアプリに触ること。
- README.md の変更。
