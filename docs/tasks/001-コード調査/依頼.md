# 001 コード調査（読み取り専用）

対象: このリポジトリ全体（Chrome拡張 Manifest V3、ビルドなしの素のJS、約3,200行）。
ファイルは一切変更しないこと。結果は -o で指定したファイルに日本語で書く。

## ねらい

これから機能を足していく前に、コードの整理と書き方の決まり（命名・フォルダ分け・検査の道具）を決めたい。
その判断材料として、今のコードの実態と、整理の案を出してほしい。

## 調べること

1. ファイルどうしのつながり
   - content script 間（MAIN world と ISOLATED world、同じ world 内）で、何を通じてやり取りしているか（window の global、postMessage、CustomEvent、chrome.runtime など）。名前空間やメッセージ型の一覧。
   - manifest の読み込み順に依存している箇所。
2. 命名の実態
   - 変数・関数・定数・DOM の id/class・CSS カスタムプロパティ・メッセージ型・storage キーの命名の型と、揺れている所（具体的な箇所つき）。
   - 外に保存・公開されていて、変えると利用者の保存データが失われたり動かなくなる識別子（chrome.storage のキー、DOM id など）の一覧。
3. 構造の問題
   - 大きすぎるファイル（review-ui.js 788行、graphql-page.js 762行など）を分けるなら、どの責務の境目で分けるか。
   - 重複した処理、使われていないコード、役目が名前と合っていないファイル。
   - probe（診断ページ）と background.js が今も必要な役目を持っているか。
4. 検査の道具
   - ビルドなしの素のJSの Chrome 拡張で、整形と lint をどう入れるのが一般的か。Biome（既定設定）で足りるか、ESLint 等の方がよいか。Chrome の API や content script の global の扱いで問題が出るか。
   - 実際に既定設定で当てたら何件くらい違反が出そうか（推定でよい。実行できるなら実行してよいが、ファイルは書き換えない）。
5. 参考
   - Chrome 公式の拡張サンプル（GoogleChrome/chrome-extensions-samples）や、広く使われているビルドなしの拡張のフォルダ構成・命名を検索して比べる。出典の URL を残す。

## 書いてほしいこと

- 上の1〜5の結果（事実と推測を分ける）。
- 整理の案を2つ程度（小さく直す案と、もう少し踏み込む案）。それぞれの手間と危険（動作が変わる可能性）。
- 決まりとして文書に書くべきこと（コードを見ても分からないこと）と、検査の道具で守らせるべきことの区別。
